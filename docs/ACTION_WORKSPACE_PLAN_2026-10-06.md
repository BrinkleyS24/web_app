# Action context and editable outreach

Status: implementation and local verification complete; staged and public authenticated draft acceptance passed. Backend is live at 100% latest traffic; web publication is pending.

## Implementation and dependencies

1. Carry the existing 16-character hexadecimal logical and evidence-version keys in internal Apply Gate/Resumes links. Do not put company names, message text or recruiter addresses in URLs. Resolve the current action through the existing owner-authenticated queue; never trust query parameters as authorization or copy an old action payload into a new job.
2. Show a shared destination banner with the job, purpose, evidence and return path. Seed an initially empty Apply Gate form from a current version-matched task's known company/title/public job URL; do not invent a posting, overwrite typed inputs or change a resume selection. Completion remains an explicit claim after doing the work, persisted through the existing complete endpoint. Opening a tool, generating/copying a draft or opening Gmail never completes it. Changed, blocked, deleted and unavailable actions retain recovery instructions without an enabled completion button.
3. Make subject, message and signature editable. Preserve separate edits per account, task evidence version and preset in the existing in-memory QueryClient, with a bounded lifetime and logout cleanup. Do not save message bodies to browser storage or add server draft retention. Reload ends this editing session; cross-device/reload draft persistence is outside this release and must not be advertised.
4. Remove the backend's literal name placeholder. Use the user's editable display name only when available; otherwise require a signature before copying. Reject unresolved fill-in placeholders and empty content. Copy the edited content, including its signature, and open only the existing Gmail thread for manual paste/review/send. Keep recipient warnings and source evidence visible. Feedback remains about the generated draft, not silently uploaded user edits.
5. Extend the draft request compatibly with an optional pair of logical/version keys. For the new workflow, validate the owner-current queue version and exact thread/action/email/application selectors before generating; refuse a disappeared requested thread instead of selecting a different conversation. Include existing corrected company/role fields in the draft source read. Legacy requests remain supported. This adds one queue read per new draft generation, using the existing pipeline; no database migration, new OAuth scope, Gmail send permission, new model call or dependency update. Test navigation, durable completion, recovery, editing/copying, preset isolation, account isolation, stale draft requests, late responses and narrow-screen layout. Build/typecheck and appropriate backend regressions precede any release.

## Failure, security and operational review

| Area and failure mode | Impact | Mitigation | Graceful fallback |
|---|---|---|---|
| Dependency: tool link drops identity or queue has no action | Generic work is attributed to the wrong task. | Shared link builder; authenticated resolution by exact logical/version keys; no inferred company/title match. | Tool remains usable; banner directs back to Next Actions and cannot mark an unknown task done. |
| Failure: queue unavailable or save rejected | False success or disappearance of work. | Explicit loading/error state, no automatic mutation retry, validate success envelope, keep completion independent of refetch. | Retry context load/save; preserve context and edited content. |
| Edge: task deleted, expired, blocked, done or evidence changed | A stale tab completes another version or repeats work. | Check current effective status and version; server already rederives the owner queue and rejects stale sensitive actions. | Show already saved or review/return state; never silently adopt a new version. |
| Security/privacy: forged query keys, cross-account cache, draft persistence | Foreign attribution or exposure of inbox-derived text. | Opaque key validation, owner-scoped queries, authenticated backend, drafts only in memory, clear private draft cache on logout/account change; no recipient/body in compose URLs or logs. | Reject malformed context; clear editing session; require fresh signed-in evidence. |
| Race: repeated completion click, refetch changes action, late generation after preset/account switch | Duplicate claims or edits overwritten by an unrelated response. | Synchronous submission guard; send original version; draft keys include evidence version/preset; ignore responses after unmount/account change. Existing completion is a user claim, not proof an email was sent. | Keep first confirmed result; stale response asks for review; retained edits remain attached to their original preset/task. |
| Draft source: missing thread silently selects another application conversation, or stale selectors disagree with queue | A draft appears under the wrong job/contact. | Optional version pair is required together; authenticate owner queue, match original version and exact selectors, and refuse application-thread fallback for reference-bearing requests. Include corrected metadata. Generation is a read, not a frozen transaction or a send. | Return refresh/review without a draft; old requests retain compatibility. The user must still check the actual conversation before sending because new mail can arrive later. |
| Async: completion committed but refresh failed, network timeout, clipboard blocked | Misleading failure or lost edits. | Treat successful save separately from background invalidation; no success toast before response; clipboard errors surfaced. | Retain task/context; retry/read current saved state; select and manually copy text if browser clipboard fails. |
| UX: missing signature, unresolved placeholder, regeneration, copied draft marked sent | Unfinished messages sent or fabricated progress. | Explicit editable signature, placeholder/empty-content checks, edits isolated per preset, clear copy/manual Gmail labels and generated-version feedback wording. | Require fields to be completed; keep editing possible; no automatic send/completion. |
| Performance: extra whole-queue reads or unbounded draft cache | Added latency/memory pressure. | Reuse owner-scoped client queue cache, only load context on supported routes, one server queue preflight for a new draft, 30-minute unused draft cache lifetime and bounded edit lengths; no new AI/Gmail calls. Measure synthetic generation latency; it is not a load benchmark. | Context retry state; release unused in-memory drafts; existing tools remain usable. |
| Deployment/rollback/schema: mixed client/server versions | Placeholder drafts or unsupported APIs. | Additive optional draft-request fields only; editor handles legacy name placeholder; production builds checked. Deploy the backend guard before publishing the new client. Backend remains compatible with old clients. | Keep the reference-bearing draft rejection/validation guard when rolling back; preserve the existing outcome action-reference guard, both production flags and Firebase version 2. Old clients still lack the new draft preflight. |
| Observability/testability: mocks hide wrong copy/navigation or failures log private content | Passing tests conceal lost context or privacy leaks. | Exercise router navigation, async failures, copied bytes and account/preset separation; backend draft regressions; test synthetic inputs only. No added content telemetry. | Report verification limits; leave deployment pending if acceptance fails. |

The existing queue completion endpoint is a state record, not a transactional Gmail send. This release does not claim atomic closure plus queue completion, substantive interview preparation, a resume editor or persistent cross-device drafts. Those separate workflows need their own acceptance gates.
